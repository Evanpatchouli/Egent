## 数据与一致性

- 新增 AgentTask：UUID id、conversationId、triggerMessageId 唯一、type（分析前可空，避免伪造分类）、规定的八种 status、workspacePath、时间戳、errorMessage、受限 metadata JSONB。
- metadata 保存经过校验的分析/方案、方案版本、确认者及确认消息、已处理消息游标、当前分析子阶段、有限执行摘要。必要时将并发版本/消息游标做显式字段，避免无界消息数组。
- PostgreSQL 部分唯一索引保证每 conversation 至多一个 active task；triggerMessageId 外键/唯一约束保证消息与任务一对一。
- 在 P3 同一会话 advisory lock 与消息事务内：无 active task 时创建 PENDING；有 active 时把新消息关联到当前任务的持久处理进度，不创建第二任务。重复 clientMessageId 返回已有结果，不再触发。
- 不扫描 P4 上线前的历史消息批量创建任务。运行时 AgentService 在 server 初始化时接入；测试注入 fake service/执行器，不因运行 P1/P2/P3 测试启动真实 CLI。
- 单实例全局只运行一个 CLI invocation；持久任务表作为待处理来源，内存只用于当前执行/唤醒，不用于保存等待确认。新消息继续正常落库且 HTTP/Socket 不等 Codex。
- AgentTask 状态与对应 AGENT 消息同事务提交后广播；Agent 消息使用同一时间排序和 Conversation.updatedAt 规则，不改首条 USER 标题。Agent 回复计入未读，SYSTEM 保持不计。
- 数据库暂不可用时不能声称已成功保存 FAILED；记录错误、禁止 implementation，并在数据库恢复/重启恢复时处理未完成状态。

## 集中状态机与恢复

- PENDING -> ANALYZING -> WAITING_USER_CONFIRMATION / WAITING_OWNER_CONFIRMATION / COMPLETED（问题）。
- WAITING_* 的讨论/方案修改走只读再分析，再进入等待；复杂任务不因后续同事讨论自动降级为免 Owner 确认。
- 只有明确确认且数据库权限/任务版本/方案版本匹配，才能进入 IMPLEMENTING；IMPLEMENTING -> COMPLETED / FAILED。
- 等待中的明确拒绝 -> CANCELLED；超时、非法输出、路径/启动/执行错误等 -> FAILED。终态不能回到 IMPLEMENTING；无效 API 转换返回冲突，不破坏已完成记录。
- 所有转换集中定义并使用条件更新/版本比对，拒绝并发重复确认及过期分析结果。
- 启动：连接 DB、初始化 Socket/Agent、恢复任务后提供服务。PENDING 调度，ANALYZING 恢复为 PENDING 并保留其分析用途，WAITING_* 保持并补处理未消费消息，IMPLEMENTING 标 FAILED，提示 Owner 检查工作区，绝不自动再次执行。
- 正常关闭：停止新调度，取消正在运行的子进程并等待退出；写入中断结果；无法确认退出时不开始另一个 implementation。异常终止恢复不宣称已回滚修改。

## 三条工作流与确认

- 初始普通 USER 消息在没有 active task 时触发只读 Codex 分类，禁止关键词分类。闲聊也可分类为 QUESTION 并给出简短回复。
- A：简单开发输出简明计划/影响/风险，等待触发请求者或 Owner 明确确认。其他参与者可讨论，不能替请求者批准。确认仅针对当前方案；拒绝取消。
- B：复杂开发解释复杂性/问题，等待 Owner。同事可补充意见、请求 Owner，但不能批准、修改最终方案后直接执行；Owner 修改方案也要重新展示并再次确认。
- C：只读回答，结构化输出包含可确认标记、证据或不确定原因；无法从代码/文档确认时明确说明不确定，COMPLETED，不假装验证。
- 自然语言确认由只读 Codex 上下文判定 CONFIRM/REJECT/REVISE/DISCUSS，严格 schema 校验。含修改或含糊表达不能批准。授权身份来自数据库，模型不能授予权限。
- 确认必须发生在该方案消息之后；分析/实施期间的新消息保留到对应任务，不因实施结束被回放为新的执行请求。等待阶段按消息顺序处理，结合持久游标避免重复消费；方案更新或有未处理新意见时不能执行旧确认。
- 提供任务查询 API；自然语言为主要流程。可增加显式 confirm/cancel API，必须携带当前方案版本并做同样权限和状态检查；cancel 在运行阶段需先停止进程，明确不会回滚已写文件。

## CodexExecutor

- 接口 analyze / interpretConfirmation / implement；生产 CodexCliExecutor，测试 FakeCodexExecutor。spawn adapter 单独注入测试启动/退出/输出/取消，业务不依赖 child_process。
- CODEX_COMMAND=codex（程序名或路径，不允许拼成 shell 命令）、CODEX_TIMEOUT_MS=600000；固定 shell:false、windowsHide:true、cwd=验证后的 workspace。prompt 通过 stdin，用户内容不进入 shell/参数拼接。
- 每次调用重新检查 workspace 来自该 Conversation.projectPath、仍存在于真实 Codex projects、存在且是目录。处理 realpath/Windows 大小写及路径重定向，不根据消息中路径改变 cwd。
- ANALYZE/确认理解：read-only sandbox，明确不改文件/不运行破坏命令。IMPLEMENT：workspace-write，且必须已原子记录确认后才 spawn；不使用 bypass/danger-full-access，沙箱或审批无法满足时失败，不偷偷放宽。
- 使用非交互 exec、结构化输出 schema、JSONL stdout，从受支持的最终 assistant 输出提取 JSON 后再次运行时校验，不把整段 stdout 当对象。不申请 Egent API key，沿用本机 Codex 认证/模型配置。
- 有界输出（例如 stdout/stderr 合计 2 MiB、最终 JSON 64 KiB），超限失败；schema 限制字符串/数组长度，拒绝非法类型、未知动作、越界 confidence。执行摘要包括 summary/changedFiles/verification，不直接转发日志。
- 10 分钟默认超时与 AbortSignal 取消，Windows 清理进程树，等待 close 后释放全局执行槽。参数不受客户端控制；stdout/stderr 的错误、EPIPE、非零退出均处理。
- structured logs 只默认打印事件、taskId/conversationId/projectPath/status、exitCode/耗时与安全错误摘要；不默认打印 prompt、全量输出或凭据。
- CODEX CLI 自带用户配置可能启用外部工具/钩子；核实本机可用限制方式，分析模式不能把 prompt 当唯一只读保障，不启用额外写入目录或外部副作用能力。

1. database/schema.prisma 与新 migration：AgentTask、枚举、关联、active 部分唯一索引与必要版本/游标字段。

6. server/services/messages.ts、chat-events.ts、conversations.ts：事务任务触发、AGENT 消息、Agent 未读；routes/agent-tasks.ts、app.ts：查询及必要明确操作。
7. server/socket/chat.ts、server.ts、config.ts：提交后状态推送、初始化/关闭恢复、环境变量。
8. web/hooks/useAgentTask.ts、components/chat/AgentStatus.tsx、ConversationView.tsx：轻量状态与历史恢复；更新过时的“尚未自动处理”提示，P3 布局不大改。

10. .env.example/.env、package scripts、README、docs/p4-validation.md、.agents 记录与归档。只增加必要依赖，已有版本不升级。
